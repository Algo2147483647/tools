# AI 工作台演进与 Lean 验证方案

版本基线：0.6.0；2026-11-14。本文区分已实现能力与后续设计，不把路线图当成已交付功能。

## 当前结论

当前项目已具备流式 AI 工具循环、数学计算、数据与图表输出、AI 编写 Python、编辑器回写及设置持久化，适合单人交互式数学与文本任务。它仍然是一个有边界的本机工作台，尚不是可恢复、可审计、强隔离的长任务自主平台。React/TypeScript 改善界面结构与类型检查，但不会自动带来可靠自主能力。

本次界面迁移到 React/TypeScript：App 管理交互，Solution/RunDetails 展示运行与证据，SettingsPanel 管理配置，types.ts 定义界面数据类型。Electron 主进程、服务层和计算适配器仍为 CommonJS JavaScript；共享事件 reducer 保留现有测试。不能声称整个项目已全量 TypeScript 化。

## 已实现

- Solve 右上角指示灯显示闲置、运行、完成、失败或取消；没有 Completed 正文标记、快捷键文案或 Copy / Run again / Hide 按钮。
- 右侧逐步显示公开解题说明、答案、计算公式、图表和统计表。工具参数、代码、执行阶段、输出与校验均在 Run details，默认折叠。
- 五类数学工具与 code_workspace、editor_document 共享统一参数校验、状态、耗时、错误、诊断及附件格式。
- code_workspace 运行 AI 自己写的 Python，文件在当前会话工作区中延续；支持列出、读取、写入文件和展示 PNG。内置数学库可直接导入。错误与 stdout/stderr 返回 AI，使其可以修复再试。
- editor_document 提供 read / replace。替换携带读取时的版本；界面核对原文后回执。版本变化或界面原文不同均拒绝覆盖。支持直接回写文本或工作区 UTF-8 文件，适用于 JSON 格式化、压缩和内容改写。
- AI 配置在 userData 下持久化，API Key 通过 Electron 异步 safeStorage 加密。模型目录按服务端点和凭证身份缓存 24 小时，可主动刷新。当前只保存一个激活配置，尚非多配置账户管理。

当前 Python 运行模式具有进程资源与时间限制，不是操作系统文件隔离沙箱。工作目录和最小环境变量不等于阻止代码访问本机其他文件。工作区命令限制路径，但 AI 代码本身仍是本机用户权限进程。当前会话文件清理不保证覆盖异常崩溃遗留；后续增加启动回收和项目保留策略。

## 关键差距与优先顺序

| 优先级 | 当前缺口 | 建议实现 | 验收标准 |
|---|---|---|---|
| P0 | 本机代码缺少真正的文件与网络隔离 | Executor 后端接口；先支持 Docker/WSL2 隔离执行，后续远端容器；只挂载项目副本，默认无网络，独立资源配额 | 读取宿主秘密、越界写入、外联、进程逃逸与超限测试均被阻断 |
| P0 | 文档回写无持久版本与崩溃恢复 | 主进程 DocumentService、版本日志、差异补丁、撤销记录；用户编辑与 AI 编辑进入同一事务 | 编辑冲突不丢字；重启恢复；可撤销 AI 修改 |
| P0 | 运行仅存内存，不能断点续做 | SQLite 事件日志、任务状态机、工具幂等键、检查点和附件哈希 | 崩溃后恢复到最后已确认工具结果；有副作用的调用不被重复执行 |
| P1 | 主进程/工具接口缺少完整类型贯通 | 分层迁移到 TypeScript；运行时 schema 成为 IPC、工具声明和事件类型唯一来源 | 不一致参数在编译与边界验证两层发现；移除重复定义 |
| P1 | 固定短循环缺少长任务规划 | 显式任务、子目标、预算、重试与停止条件；维护证据和待验证结论 | 困难任务可解释地停止；工具失败可修复；不无限循环 |
| P1 | 缺少正式证明能力 | 下述 Lean 工程、检查服务与信任分层 | 对真/假/未完成/额外公理证明给出不同状态 |
| P1 | 只有测试成功率，没有任务质量评估 | 建立数学、数据、编辑、证明回归集；评估正确率、成本、延迟、恢复率 | 每次发布有同一基准下的可比较结果 |
| P2 | 模型上下文与项目知识缺少管理 | 项目级文件索引、检索、上下文压缩和来源引用；多模型路由 | 结果能追溯原始文件与版本，摘要不能替代证据 |
| P2 | 扩展生态与发布治理不足 | 工具插件清单、能力权限、版本兼容、签名更新和安装包追踪 | 新插件不需要修改核心；升级可回滚，工具权限可审计 |

先完善隔离、事务和可恢复性，再增加更复杂的自主规划。多代理协作应由任务收益决定，不能用代理数量代替平台可靠性。

## Lean：完整接入方案（尚未在此版安装）

### 1. 工程与版本

每个证明项目保存 lean-toolchain、lakefile、lake-manifest、源文件与依赖哈希。固定 Lean 与 mathlib 的兼容版本，不在一次证明任务中自动升级。依赖安装属于工程准备阶段；运行阶段使用预热缓存且关闭网络。Windows 前端仍用 Electron，Lean 执行放入与 Python 相同的隔离 Executor 后端。工具未安装时返回 runtime_missing，不能伪造验证成功。

### 2. 接入统一工具接口

- lean_project：创建/查询固定模板工程、工具链与依赖状态；只允许安装已声明版本。
- lean_check：编译指定工作区文件和命题，返回带行列的 errors/warnings、退出码、耗时、版本、源文件哈希及证明状态。
- lean_goals：经 Lean language server 读取光标处 goals、局部上下文与诊断；任务结束关闭会话。
- lean_search：在固定 mathlib 索引中检索引理、签名、命名空间、文件与版本；每个命中有出处。
- lean_audit：对目标定理提取公理依赖，标记 sorryAx、非允许公理及扩展信任链；按等级调用独立检查器。

所有结果使用现有统一 envelope，附件新增 proof_report 和源代码文件。AI 通过工作区写 Lean 源文件，执行检查，依据诊断修复并重检；诊断必须引用当前文件哈希，旧文件的成功结果不能复用到新文件。

### 3. 信任状态

proof_status 分成：runtime_missing、syntax_error、goals_remaining、accepted_with_assumptions、kernel_checked、independently_checked。执行 status=ok 仅表示检查程序运行成功，不等同于证明通过。

成功策略至少检查：目标声明确实存在且类型与锁定命题一致；无未完成目标；目标的传递公理依赖中没有 sorryAx；非基础允许公理必须列出；编译器/原生计算信任扩展必须单独记录。允许公理清单随工程策略固定，不能由生成证明的 AI 自行放宽。只搜索源码中的 sorry 或只检查编译退出码均不足以建立可信性。

正式命题与自然语言问题的对应关系必须单独展示。即使 Lean 验证通过，也只能证明形式化命题在列出的定义与公理下成立，不能证明 AI 翻译问题时没有改变条件。

### 4. 更高等级复核

普通检查先建立编译和公理审计闭环。面向未经审查的 AI 生成代码，进一步采用 lean4checker 重新检查环境，或 comparator 配合外部检查器验证目标命题与证明产物；检查器与生成器分离，不相信 AI 打印的“通过”字符串。检查器支持范围和信任基座应写入 proof_report。Lean 元程序也能执行任意操作，因此 Lean 与 Python 都必须在执行隔离层内运行。

### 5. 交互

右侧正文展示命题、当前目标、关键诊断和最终证明报告。Run details 展示每次调用、版本、代码差异、错误、耗时、公理依赖与复核等级。回写编辑器使用现有 revision 检查；长期改为可撤销补丁。工具链准备进度属于设置或工程页，不混入解题正文。

### 6. 验收用例

包括算术恒等式、归纳证明、mathlib 引理应用、错误命题、显式 sorry、间接引用 sorry、私自新增公理、修改命题再证明、旧诊断错配、无限 tactic、资源超限、取消、崩溃恢复、依赖版本不匹配，以及伪造日志输出。每个用例同时验证界面状态、审计字段和是否被计为通过。

### 7. 分阶段交付

L1：固定工具链 + lean_check + 行列诊断 + 来源哈希 + 超时/取消。
L2：goals/search + AI 修复循环 + 公理审计 + 锁定命题比较。
L3：独立检查器 + 隔离项目缓存 + 可恢复证明任务 + 完整回归基准。

L1 只能标记“编译检查”，不能标记“独立证明验证”。L2/L3 的标签须由实际执行证据决定。
