# Layout architecture

`src/layout` turns graph documents and view settings into renderable stage data. Modules are grouped by chart family; controllers own React state and asynchronous job lifecycles.

| Directory    | Responsibility                                                                              | Entry point                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `shared/`    | Stage contracts, algorithm contracts, appearance, selection, text fitting and edge geometry | [Stage types](../src/layout/shared/types.ts), [algorithm types](../src/layout/shared/algorithm-types.ts)   |
| `node-link/` | Node-link preparation, algorithm dispatch, node creation, positioning and stage assembly    | [layout.ts](../src/layout/node-link/layout.ts)                                                             |
| `sankey/`    | Flow layout and Sankey stage construction                                                   | [layout.ts](../src/layout/sankey/layout.ts)                                                                |
| `compound/`  | Hierarchy layout, declarative constraints, automatic selection, validation and routing      | [layout.ts](../src/layout/compound/layout.ts), [layout-solver.ts](../src/layout/compound/layout-solver.ts) |
| `timeline/`  | Time-axis preparation, event arrangement, labels, routing and stage construction            | [layout.ts](../src/layout/timeline/layout.ts)                                                              |
| `spatial/`   | Coordinate projection and spatial stage construction                                        | [layout.ts](../src/layout/spatial/layout.ts)                                                               |
| `workers/`   | Worker entry points and shared request/response contracts                                   | [protocol.ts](../src/layout/workers/protocol.ts)                                                           |

## Construction pipelines

Node-link construction runs through `input.ts` → `nodes.ts` → `position.ts` → `stage.ts`. `algorithm.ts` dispatches to the existing Dagre, level and Sugiyama implementations in `algorithms/`. The public `buildStageData` entry also retains Sankey validation/fallback and spatial dispatch.

Timeline construction runs through `prepare.ts` → `arrange.ts` → `stage.ts`. `prepare.ts` resolves selection, time bounds, settings, fonts and the axis. `nodes.ts` creates event nodes using that prepared context. `arrange.ts` allocates channels, applies explicit positions and packs labels. `stage.ts` assembles edges, bounds and orientation; `edge-routing.ts` owns edge anchors and route construction. Pipeline objects are local, mutable construction state: arrangement updates event positions and stage assembly adds edge ports to nodes. They are not persisted documents.

Graph documents contain only a `metadata.layout` path association. The independent version 3 Layout file declares one chartType and contains only its configuration and complete rendering; version 1 declarations remain readable. `schema/layoutProtocol.ts` validates the envelope and `schema/layoutGeometry.ts` captures/reconstructs geometry, rebuilding runtime Maps and indexes. The Layout title has Update current layout, and the Schema tab shows field descriptions and the actual current JSON. Update writes a sibling `<graph>.<chartType>.layout.json` or overwrites the existing association without a file picker. Save the graph to persist a newly created association. See [Layout protocol](layout-schema.md).

`compound/layout.ts` measures nodes and labels and creates a fresh topology problem. `compound/automatic.ts` routes the baseline, searches bounded alternatives, validates geometry and selects one result. `layout-solver.ts` keeps candidates internal. The controller sends each fresh problem to a Worker and installs geometry and quality together. There is no accepted snapshot, cross-view geometry cache, pin capture, or user review lifecycle. Zero requested spacing retains a minimum routing corridor.

`useCompoundStage` coalesces input changes, cancels superseded jobs and discards stale responses. Its result contains only the current stage. `useCompoundLayoutPlan` runs the dedicated compound planning harness, transfers its final computed stage to the live renderer and commits only its declaration. The matching input key prevents another calculation after commit. Intermediate solves remain transient and never become history entries.

## Types and text measurement

`shared/algorithm-types.ts` describes algorithm coordinates and routes. `shared/types.ts` describes renderable stages, and re-exports algorithm and timeline types for shared consumers. Timeline-specific stage fields live in `timeline/stage-types.ts`; its dependency on `StageData` is type-only.

Browser Canvas access and its cached measurement context live in [shared/text-measurement.ts](../src/layout/shared/text-measurement.ts). `shared/text-estimate.ts` supplies the deterministic width estimate for environments without Canvas, while `shared/text.ts` retains the text fitting API. Compound worker inputs contain measured rectangles and edge-label sizes; timeline candidates reuse measured baseline label widths and display titles. Other worker text measurements retain the deterministic fallback.

## Worker boundary

Requests have `{ jobId, payload }`. Responses are either `{ jobId, ok: true, result }` or `{ jobId, ok: false, error }`. The worker handler echoes the request ID and converts synchronous failures into error responses.

Controllers retain cancellation, termination, timeout handling and graph/view freshness checks. Both controllers ignore responses for a different job ID. The timeline worker also restores graph indexes lost during structured cloning before evaluating a candidate.

The candidate controllers share main-thread request cleanup in `app/layout/workerJob.ts`. Compound automatic arrangement uses its existing 15-second timeout. Timeline evaluations have no application calculation timeout or event/relationship count ceiling. Model generation has no application deadline; users can cancel it. Cancellation settles the request and terminates its worker. Graph/view revision checks remain in each controller.

## AI layout rules

`compound/ai/protocol.ts` and `timeline/ai/protocol.ts` define separate schemas and semantic validation. Their request modules build chart-only context. Generic Console/editor prompts, command parsing, history and working memory never enter Layout requests. Compound AI may design exact positions or delegate placement through structural preferences; workers measure and execute the design.

Compound plans optionally include `placements: [{nodeId,x,y}]`. Coordinates are exact pixel offsets from the parent's content origin (root: 36/36, group: 24/58). The context supplies local and absolute positions, measured dimensions, minimum group dimensions and padding. With placements present, `compound/precise.ts` preserves unspecified observed local positions, fits groups bottom-up, translates descendants and routes connections. It never runs topology selection or moves specified positions to repair overlaps. Invalid geometry returns concrete errors to the model for revision; soft direction preferences provide diagnostics only. An empty placements array keeps positions and reroutes; omitting placements delegates to Automatic's topology solver.

Coordinates remain outside graph JSON. Update current layout persists exact selected geometry in the separate Layout file, including group bounds, routes and labels. On reload, matching graph/settings/scope restore it. Graph, view or layout-setting changes use fresh geometry; a live Appearance geometry change also invalidates the restored rendering. Selecting an earlier trial installs that exact computed stage. Coordinate trial reuse also keys the observed baseline, since omitted positions refer to that observation.

Compound plans can select expanded-group directions, partial sibling `flow-order` sequences, and routing preferences. A flow order adds precedence between its named siblings; all real connections remain available to ranking, packing and refinement. Unlisted siblings keep their topology instead of becoming a forced chain. Contradicting relationships may become feedback connections without changing the graph. Editable scopes, semantic types/descriptions, live node measurements, current constraints, endpoint positions, detours, crowded ports and inter-group connections accompany the request. These measurements are transient observations, never saved declarations. A plan replaces constraints only for supplied scopes and edge IDs, so an empty plan retracts those preferences while preserving unsupplied configuration.

`compound/ai/workflow.ts` implements an AI-controlled evaluate/observe/select session. The model returns `evaluate` with a complete plan and a short hypothesis, receives all measured metrics, changes from the starting layout, diagnostics and routing hotspots, then chooses its next action. There is no threshold deciding whether feedback is sent: every solve is observed. `finish` selects an existing successful candidate (or explicitly `current`) and a user-facing assessment. The harness does not rank plans or replace that selection with Automatic. Failed evaluations are reported and cannot be selected; malformed continuation, cancellation or exhaustion without a selection leaves the live canvas unchanged instead of silently applying an earlier trial.

The session permits four evaluations and six decisions without a generation deadline, with the final decision reserved for selection. Each decision retains one bounded JSON correction (at most twelve provider requests). Duplicate plans reuse transient computations. Intermediate trials remain transient. Explicit Update persists only the current selected rendering. Only the selected declaration and stage are committed. No user Review step is required. AI direction choices are stored as replaceable scope constraints; the direction selector remains the user's policy, so a model can revise its own earlier choice on subsequent runs.

An outer-route preference adds nearby corridor candidates with a finite cost bonus and a detour bound (at most 1.35 times the shortest ordinary route cost plus 48). It never allocates a full-canvas bottom lane or grows the canvas. Separate label-placement fallback can still allocate space when visible labels need it.

For delegated placement, the local solver compares a finite combination of route length, shared length, crossings, bends and content extent when resolving geometry within a declaration. Exact placement bypasses that position ranking. This is distinct from the AI's final choice among evaluated declarations. Candidate bounds are rebuilt from placed content, fixed out-of-scope routes and the configured minimum canvas. Observations distinguish actual route extents from unused minimum-canvas space and report the full metric vector without prescribing a decision.

Connection-port mode is an application-controlled declaration shared by baseline and candidate routing. `midpoints` supplies only side-center endpoints; `distributed` additionally supplies separated offsets. The AI observes this mode but cannot override it. Selecting Automatic clears AI decisions and restores automatic direction before a fresh local solve; objective and port mode remain unchanged.

`layout/shared/ai/request.ts` owns a two-call budget per decision: one request and at most one regeneration for syntax, schema, semantic or truncation errors. A provider rejecting schema output can use the remaining call in JSON text mode. The entire response must be one object; fences, multiple documents and JSON-encoded strings fail. Broken output is not replayed in correction prompts. Compound planning enables DeepSeek thinking through its [thinking-mode API](https://api-docs.deepseek.com/guides/thinking_mode), without a fixed application output cap. Layout reads the selected service model metadata and uses its advertised output capacity. Optional limits are omitted when capacity is unavailable; Ollama uses num_predict=-1. Anthropic requires max_tokens, so unavailable model capacity produces an explicit error rather than a guessed fallback. Timeline planning also enables DeepSeek thinking; Console uses the same provider-capacity policy. Error details include actual limits and available usage counts. Cancellation, refusal and transport errors terminate immediately. Field paths, attempt count, finish reason and request ID support diagnostics.

`ai/transport/providerTransport.ts` normalizes content, structured values, completion/refusal metadata and usage. Anthropic, Gemini and Ollama receive their schema output options; OpenAI-compatible endpoints use JSON object mode because compatibility does not guarantee schema support. Worker and algorithm modules do not import network request entry points.

Layout and Console requests stream through `ai/transport/streaming.ts`, which decodes SSE or Ollama NDJSON across UTF-8 chunk boundaries. Provider-supplied reasoning and response text are separate transient UI previews; the UI retains complete reasoning and response text for every request in the run. Neither the stream reader nor the JSON parser imposes a byte/character ceiling. Start/end events flush pending text immediately. Completed transcripts survive panel closing and mode changes until a new run or document starts. The UI does not invent reasoning when the service omits it. Cancellation closes the reader. Malformed events, provider stream errors and missing completion markers reject the response; only a completed response can pass JSON validation and execute. Services that return a complete JSON envelope instead of streaming remain supported.

The compound controller retains a session-only run report: trial hypotheses, failures, metrics, final selection and assessment. Before/selected/delta values share one quality table. Node/group and route changes are measured against the run's starting geometry, not the selected candidate against itself. Explicit `current`, unchanged trials and changed geometry have distinct outcomes. Reports remain visible after commit; after recomputation their historical metrics are labelled separately from current quality, including when settings are later reverted. Reports contain metrics and text, not saved geometry.

The editable AI model picker queries the configured service's model catalogue on opening and supports refresh, pagination, keyboard selection and custom IDs. Catalogue failures never overwrite the selected model or substitute a preset as a verified available model. Changing the provider, endpoint or credentials invalidates the list and cancels its request.

Layout input preserves the complete visible graph, labels, descriptions, routing findings and user instructions; there is no node/edge sampling or character clipping. The same applies to timeline context and ordering. Provider context/output capacity still applies, and a provider-reported truncation is not accepted as a valid completion even if the partial JSON parses. Correction requests retain design intent without imposing reduced plan sizes. User cancellation, structural validation, iteration counts and local Worker computation limits remain in effect.

AI connection settings contain only provider, base URL, model and API key. Legacy Execution, Temperature and Console output-token settings are discarded on load. Requests omit temperature and use service sampling defaults. Console editing requests validate and execute commands directly, with undo and applied-result reports; questions return answers without edits. Invalid or stale batches are never executed. Console graph summaries and supplied conversation history are sent without local clipping.

Timeline AI uses `timeline/ai/workflow.ts`: evaluate → observe measured metrics and exact geometry → revise → finish. The visible default prompt describes these capabilities. Plans can contain exact cross-axis event positions, independent physical label positions and complete connection polylines. Only timestamps, durations, graph content, explicit pins and route attachment semantics are fixed. An evaluated result is selected by the model and applied directly as one undoable layout edit. There is no Review modal or automatic quality ranker. The model controls iteration without a fixed round budget; cancellation and stale-document guards terminate work. Provider reasoning/response streams remain inspectable after completion. Quality and before/current measurements appear in Layout.

A timeline plan's `basis` identifies the graph, time settings and measured layout inputs used for exact positions. Changed inputs retain semantic ordering preferences but drop stale exact placements/routes; this prevents old temporal endpoints from breaking a newly configured time axis. No graph-edit command strings are generated.
